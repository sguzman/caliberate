# 0010.2 — Align pane config validation with runtime geometry and verify narrow-window yielding

## Why

Human runtime acceptance of task `0010.1` found a concrete persistence failure:

- GUI runtime now allows Browser/Details auxiliary panes down to 200 px.
- `ControlPlane::validate()` still requires:
  - `gui.pane_left_width` between 320 and 2400;
  - `gui.pane_right_width` between 280 and 2000.
- Dragging Details below 280 px therefore updates GUI state and then fails config persistence with:
  - `invalid config: gui.pane_right_width must be between 280 and 2000`.

The same mismatch exists for the left pane below 320 px.

The human also observed that ordinary window resizing did not visibly change pane width. The intended semantics must be made explicit and verified: preferred pane widths remain stable while the central library still has enough room, but auxiliary panes must yield toward their runtime minimum once preserving the preferred width would starve the central library.

This is a runtime-acceptance patch after `0010.1`. Do not repurpose task `0011`.

## Required behavior

### 1. Config validation must accept the runtime minimum

Update GUI config validation so persisted auxiliary widths at the runtime minimum are valid.

Required lower bound:

- left auxiliary preferred width: 200 px;
- right auxiliary preferred width: 200 px.

Do not make existing valid high/stale persisted values suddenly fail to load. Preserve backward compatibility with legacy upper bounds unless there is a narrowly justified normalization path.

At minimum:

- 200 must validate for both left and right;
- values below 200 must fail;
- existing legacy values such as 900 or 1600 must continue to load.

Do not modify the user's `config/control-plane.toml`.

### 2. Preserve threshold-based resize semantics

The expected model is **not proportional scaling**.

Example:

- if Details prefers 400 px and the window still leaves >= ~480 px for the central library, Details should remain ~400 px;
- when the window becomes narrow enough that 400 px would starve the center, the effective Details width should shrink toward 200 px;
- when the window widens again, the preferred 400 px width should return;
- temporary runtime shrink must not overwrite the preferred width.

Keep the preferred/runtime separation introduced by the corrected `0010.1`.

### 3. Ensure effective runtime bounds actually affect the rendered panel

Inspect the current egui panel behavior.

`LibraryView::ui` computes effective widths and max widths, but the human observed no visible pane-width response during ordinary window resizing.

Determine whether the current `.default_size(...)` / `.max_size(...)` usage actually enforces the computed runtime maximum after the panel has an egui-memory width.

If the existing panel API already enforces the threshold behavior correctly, do not add unnecessary machinery; document the threshold and leave it.

If persisted egui panel memory can keep the pane wider than the computed effective/max width, make the smallest correction so:

- computed runtime max is physically respected;
- separator drag remains usable;
- preferred width persistence semantics remain correct;
- no per-frame config rewrite occurs.

Do not make panes scale continuously with every window-size change.

### 4. Preserve task 0010.1 behavior

Keep:

- Library in the central area;
- Browser/Details direct header collapse controls;
- restore through layout controls;
- draggable separators;
- 200 px auxiliary runtime minimum;
- 720 px runtime hard maximum;
- ~480 px central target when physically possible;
- long Details text wrapping;
- preferred-width restoration after temporary shrink;
- complete shell dirty detection.

## Tests

Add focused tests.

At minimum prove:

1. config validation accepts left/right width = 200;
2. config validation rejects a left/right width below 200;
3. legacy high values currently accepted by config remain accepted;
4. geometry keeps a normal preferred width unchanged while central space is sufficient;
5. geometry shrinks an auxiliary width when preserving it would violate the central target;
6. widening again restores the preferred width rather than the runtime-clamped width.

If an egui-level deterministic test can prove the panel max is respected without brittle pixel snapshots, add it. Otherwise leave that part for human runtime verification and state so explicitly.
