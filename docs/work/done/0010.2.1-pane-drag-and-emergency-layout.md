# 0010.2.1 — Distinguish real pane drags from runtime clamping and degrade narrow layouts cleanly

## Why

Human runtime testing after accepted task `0010.2` exposed two remaining GUI layout defects.

### Defect A — Browser preferred width does not persist after restart

The corrected `0010.1` / `0010.2` persistence guard currently records a pane width only when:

```text
runtime_max_width >= preferred_width
```

This protects preferred widths from temporary window-induced clamping, but it fails for stale legacy preferences above the new runtime hard maximum.

Example current state:

- legacy preferred left width may be ~1864 px;
- current runtime hard maximum is 720 px;
- Browser is physically rendered at <=720;
- user drags Browser to ~250 px;
- guard refuses to save the drag because 720 < 1864;
- restart restores the stale legacy preference instead of the user's actual drag.

The implementation must distinguish a **genuine user separator drag** from an **automatic runtime clamp**.

### Defect B — impossible-width fallback mangles the central library

With both Browser and Details visible, current constraints are approximately:

- Browser runtime minimum: 200 px;
- Details runtime minimum: 200 px;
- central library target: 480 px.

When the whole window is narrower than the sum of those demands, the current layout keeps both auxiliary minimums and allows the center to collapse into unusable geometry (observed as black empty space and vertically wrapped "Library" text).

The 200 px user-facing minimum is intentional. The mangled central fallback is not.

## Product rule

The central Library remains primary.

Normal behavior:

- preferred auxiliary widths stay stable while there is room;
- panes yield toward 200 px when central space needs protection;
- genuine user drag persists;
- temporary runtime clamping does not replace the preferred width.

Emergency behavior:

- if the window is physically too narrow to show all requested auxiliary panes at their 200 px minimum while retaining a minimally usable center, degrade gracefully;
- do not render pathological near-zero central geometry;
- do not permanently change the user's visibility preference merely because the window was temporarily tiny.

## Scope

### 1. Detect genuine user resize separately from passive runtime clamp

Replace the coarse `runtime_max >= preferred` inference with a mechanism that can distinguish:

- the pane width changed because the user dragged the separator;
- the pane width changed because available window width forced a runtime clamp.

Acceptable implementation approaches include:

- a direct egui resize interaction signal, if reliably available from the SidePanel response/resize handle;
- a small deterministic interaction-state helper using prior available width / prior effective width / pointer state;
- another bounded method that clearly represents user intent.

Do not persist every effective width change.

Required cases:

1. preferred 400, wide window, user drags to 300 -> persist 300;
2. preferred 400, narrow window clamps to 250 -> do not persist 250;
3. preferred legacy 1864, runtime max 720, user drags visible Browser to 250 -> persist 250;
4. widening after a passive clamp restores the preferred width;
5. a stale value above 720 must not become impossible to replace through real dragging.

Add focused regression tests for the pure/state logic used.

### 2. Add a graceful emergency narrow-window policy

The 200 px Browser/Details drag minimum remains the normal user-facing minimum.

When available width is insufficient for:

```text
active auxiliary panes at 200 each + a minimally usable central surface
```

do not allow the central Library to collapse into pathological geometry.

Choose the smallest coherent runtime-only emergency policy.

Preferred policy:

- temporarily suppress lower-priority auxiliary panes from rendering when necessary;
- preserve their configured `*_visible` preference in persistent state;
- restore them automatically when width becomes sufficient again.

Suggested priority:

1. always protect a minimally usable central Library;
2. suppress Details first when both auxiliary panes cannot coexist;
3. suppress Browser only at still narrower widths if required.

If another bounded strategy is demonstrably cleaner, it is acceptable, but do **not** permanently write auto-suppression into config.

The user must still be able to manually collapse/restore panes normally.

### 3. Keep normal 200 px drag floor

When a pane is actually rendered under normal/non-emergency conditions, the user should not be able to drag it below roughly 200 px.

The observed refusal to shrink Browser below that floor is intentional.

Do not remove that normal minimum merely to mask the emergency layout bug.

### 4. Preserve prior accepted behavior

Keep:

- Library rendered centrally;
- Browser/Details direct collapse controls;
- restore via existing layout controls;
- width validator accepting 200 px;
- 720 px hard normal runtime maximum;
- ~480 px central target when possible;
- threshold-based yielding;
- preferred-width restoration after temporary clamp;
- visibility/side/jobs persistence;
- long Details text wrapping;
- no query/service/schema changes.

## Tests

Add deterministic tests for:

1. stale preferred width above runtime max can still be replaced by a genuine user resize;
2. passive runtime clamp does not overwrite preferred width;
3. genuine resize in normal wide layout persists;
4. emergency layout with Browser + Details does not allocate a pathological near-zero center;
5. emergency suppression/restoration decisions are deterministic;
6. runtime-only emergency suppression does not alter persisted visibility preference.

Avoid brittle screenshot tests.
