## Blocker — progress is emitted after the work it claims to describe

Current CLI flow is effectively:

```rust
eprintln!("[audit] counting source dependencies...");
let audit = audit_source(...)?; // performs BOTH catalog counts AND managed verification
eprintln!("[audit] catalog counts complete");
eprintln!("[audit] verifying managed replacements...");
eprintln!("[audit] verified {} managed replacements", ...);
```

So the `verifying managed replacements...` message is printed only after verification has already finished.

This defeats the reason progress was added. With thousands of managed assets, the command could again look frozen for a long time after the first line, and then report that it is 'verifying' after the fact.

## Required correction

Put progress events at the actual phase boundaries.

Preferred narrow design:
- add an optional audit progress callback / observer to the retirement service, or a second progress-capable wrapper API;
- emit `catalog counts complete` immediately after `db.audit_source_counts(...)` returns;
- emit `verifying managed replacements...` immediately before entering the verification loop;
- emit chunk/page progress from inside the verification loop after each page, e.g. `verified/processed N managed replacements`;
- emit a final verification completion event after the loop.

Do not make the core library print directly to stderr. Keep presentation in the CLI layer; the library should expose progress through a callback/event seam.

A simple event enum is enough, for example conceptually:

```rust
pub enum SourceRetirementAuditProgress {
    CatalogCountsComplete,
    VerificationStarted,
    VerificationPageComplete { processed: u64, verified: u64 },
    VerificationComplete { processed: u64, verified: u64 },
}
```

Exact naming may vary.

Preserve the existing non-progress `audit_source(...)` API if practical, delegating to a progress-capable implementation with a no-op observer.
