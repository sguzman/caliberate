## Required correction — literal substring parity for SQL LIKE

The GUI's current `field_contains` behavior treats filter values as literal substrings.

The structured DB path currently builds patterns like:

```rust
Value::from(format!("%{}%", filter.value))
```

and uses:

```sql
... LIKE ? COLLATE NOCASE
```

This changes semantics when the filter value itself contains SQL LIKE metacharacters:

- `%` becomes an arbitrary-length wildcard;
- `_` becomes a single-character wildcard.

Example: a literal browser filter value `100%` must search for the literal percent sign, not match `100abc`.

### Required behavior

For structured string metadata filters only (Authors, Tags, Series, Publishers, Languages):

1. Escape the filter value for use inside a LIKE pattern.
2. Escape at least:
   - the chosen escape character itself;
   - `%`;
   - `_`.
3. Use an explicit SQL `ESCAPE` clause.
4. Keep the surrounding contains wildcards so semantics remain literal case-insensitive substring matching.
5. Continue binding the resulting pattern as a parameter; do not interpolate caller data into SQL.

Use one small deterministic helper rather than duplicating escaping five times.

Do not change legacy query-field semantics in this correction; this task is about the new structured filters and GUI parity.

### Tests

Add focused DB tests proving literal behavior for both metacharacters.

At minimum:

- a metadata value containing literal `_` is matched by a filter containing `_`, while a similar one-character substitution is not;
- verify at least one Include and one Exclude path so the escaping is shared correctly.
