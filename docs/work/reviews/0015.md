## 1. get_book format projection is inconsistent

`rows()` selects:

```sql
LOWER(d.format)
```

and `resolve_content()` returns:

```rust
format.to_ascii_lowercase()
```

but `primary()` returns raw `d.format`, and `get_book()` stores that raw value directly:

```rust
Ok(Some(LibraryBook {
    id,
    title,
    format,
    path,
}))
```

With the current fixture this means:

```text
list/query/summary/content -> "pdf"
get_book                 -> "PDF"
```

This violates the required single-format compatibility projection.

### Required correction

Normalize the projected format to lowercase in one shared source-specific seam so list/get/search/query/summary/content cannot drift.

Add an explicit regression test using uppercase Calibre `data.format`.

## 2. Relation-backed string sorts are not case-insensitive across books

For Authors/Tags/Series the subquery chooses the first related value with `COLLATE NOCASE`, but the final scalar expression returned by `sort_expr()` does not carry `COLLATE NOCASE`.

Publisher and Languages have the same problem.

Example current shape:

```sql
COALESCE(
  (SELECT a.name ... ORDER BY a.name COLLATE NOCASE ... LIMIT 1),
  ''
)
```

The outer ORDER BY therefore compares the resulting book sort keys using SQLite's default binary collation.

This does not match the established Database backend semantics from task 0011.

### Required correction

Ensure final semantic sort keys for:

- Authors
- Tags
- Series
- Publisher
- Languages

are ordered case-insensitively across books.

Keep:

- Series secondary `series_index` direction behavior;
- non-ID `books.id ASC` final tie breaker;
- requested direction on the semantic key.

Add fixtures whose case would produce a different BINARY vs NOCASE order and assert ascending/descending behavior.

## 3. Legacy identifier parity is incomplete

The existing Database backend legacy identifier query matches:

```text
identifier value OR identifier type
```

The attached-Calibre backend currently matches only:

```sql
z.val LIKE ?
```

Task 0015 required the complete current `LibraryQuery` read surface, not a reduced identifier interpretation.

### Required correction

Match the existing legacy semantics against both:

- `identifiers.val`
- `identifiers.type`

with the same bound contains pattern.

Add focused tests for matching by value and by type.

## 4. data.format must be treated as untrusted path metadata

`safe_path()` validates `books.path` and `data.name`, but then directly appends:

```rust
format!("{name}.{}", format.to_ascii_lowercase())
```

without validating `data.format`.

Because format text comes from the external database and becomes part of a filesystem path, separators/traversal inside it can create additional path components. The final lexical `starts_with(root)` check is not sufficient protection in the presence of unresolved parent components.

The safety invariant is:

> no Calibre metadata value used to construct a content locator may cause the resulting path to escape the configured library root.

### Required correction

Validate the projected format before using it as a filename extension.

At minimum reject:

- empty format for a row that otherwise claims a content file;
- `/`;
- `\`;
- rooted/prefixed/path-component forms;
- parent traversal.

Normal Calibre format identifiers such as `EPUB`, `PDF`, `AZW3`, `MOBI`, and other single-component identifiers must continue to work.

Add a synthetic unsafe-format regression proving no escaping locator is returned.
