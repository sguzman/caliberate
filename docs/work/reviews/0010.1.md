## Defect 1 — runtime shrink currently overwrites preferred width

The task explicitly requires:

> Do not permanently overwrite the user's preferred stored width merely because the window was temporarily small unless the pane was actually resized by the user.

Current implementation violates this.

Path:

1. `LibraryView::ui` computes a runtime-clamped width.
2. The side panel is constrained by `.max_size(max_width)`.
3. `record_pane_width(... panel.response.rect.width())` records the resulting constrained width.
4. `CaliberateApp::pull_layout_from_library()` copies that width into outer shell state and marks shell config dirty.
5. `sync_shell_config()` saves it.

Therefore a temporary narrow window can permanently replace (for example) a preferred 600 px width with a runtime-constrained 200–300 px width.

### Required correction

Keep **preferred/persisted width** distinct from **runtime effective width**.

Persist a changed width only when it represents a genuine user resize, not merely a runtime clamp caused by insufficient available width.

A compact acceptable approach is to prevent recording an effective width when the current runtime max is below the stored preferred width, while still recording normal user drags when the preferred width fits within runtime constraints. If egui exposes a more direct reliable resize interaction signal, that is preferable.

Add focused regression tests proving:

- preferred width survives temporary narrow-window runtime clamping;
- a genuine resize in a sufficiently wide window updates the preferred width;
- restoring window width uses the prior preferred width.

Do not continuously save runtime-clamped geometry.

## Defect 2 — direct pane collapse does not reliably persist

The task requires direct Browser/Details collapse to persist through the existing config mechanism.

Current implementation sets `browser_visible` / `details_visible`, `layout_dirty`, and `config_dirty` in `LibraryView`.

However:

- `LibraryView::sync_gui_runtime_config()` does **not** write `pane_browser_visible`, `pane_details_visible`, pane sides, or pane widths.
- `CaliberateApp::pull_layout_from_library()` copies visibility state from `LibraryView` but marks `shell_config_dirty` only when left/right widths changed.
- Therefore collapsing a pane without also changing a width can remain only in memory and be lost on restart.

### Required correction

Make `CaliberateApp::pull_layout_from_library()` detect changes to all shell pane state that must persist, including at minimum:

- Browser visibility
- Browser side
- Details visibility
- Details side
- Jobs visibility
- left preferred width
- right preferred width

Mark `shell_config_dirty` when any of those values changes before copying the new values.

Add focused tests where practical for the pure/state-comparison logic. If app-level tests are not practical, keep the implementation small and document the exact persistence path in the report.
